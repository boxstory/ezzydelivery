## 07:04 — Password strength meter on Change Password
The Change Password page used to show Django's four validator sentences as a flat block of grey help text under the New Password field, with no feedback until you submitted. Replaced that with a live strength widget: a four-segment meter (Weak red → Fair amber → Good lime → Strong green), a strength label, and a checklist whose empty rounded boxes fill with a green check as each rule is satisfied. ## 07:17 — Password rule: no repeated characters or patterns
`aaabbbA@1234` used to sail through every check — 12 characters, mixed case, a digit, a symbol — and read as Strong. Added a sixth checklist rule that rejects two shapes of padding: three or more identical characters in a row (`aaa`, `111`, `!!!`) and any 2-to-4 character unit repeated back to back (`abab`, `1212`, `Ab12Ab12`). Failing it drops the meter straight to Weak and holds the submit button, same as the other rules. The 2-4 character window was picked by testing both regexes against a set of realistic Qatari-flavoured passwords: it catches every padded example without a single false positive on the good set, where a 2-3 window missed `Ab12Ab12` and anything wider added nothing.

## 07:34 — Password rule: reject dictionary words in costume
Called out on the review that `Qatar2026!` was reading "Good" — it ticked every composition box while being the most predictable shape a password can have: a capitalised dictionary word, a year, a trailing "!". Added a "Not a guessable word or sequence" rule that strips the decoration and looks at what is left. ## 07:52 — Warn existing users whose password is weak, with 3 skips
New accounts get the strength rules at signup, but nobody already registered was affected. Since a stored password is only a hash, the check has to happen at the one moment the plaintext exists — login. A `user_logged_in` receiver runs the submitted password through `core/password_strength.py`, a Python mirror of the client rules (same word list, same repeat/sequence/composition checks, plus whatever `AUTH_PASSWORD_VALIDATORS` is configured with), and stores a single boolean on the profile. The failing reasons are deliberately **not** stored — knowing why a password is weak narrows the guesses if the database ever leaks.

A flagged user hitting any normal page is sent to `/password/weak/`, which explains the new rules and offers "Change Password Now" or "Skip for now — N of 3 left". Skipping snoozes the warning for the rest of that session and burns one of three permanent skips; once they are gone the button disappears and the middleware keeps returning the user to the page until the password changes. Changing to a strong password clears the flag and resets the counter immediately, via allauth's `password_changed`/`password_set`/`password_reset` signals.

The middleware is deliberately narrow — GET only, HTML only, never AJAX, and skipping `/static/ /media/ /api/ /admin/ /accounts/ /password/ /waha/` — so no redirect loop can strand anyone and signing out is always reachable. `WEAK_PASSWORD_WARNING_ENABLED` turns the whole thing off from the environment without a deploy. `core/signals.py` was NOT imported by the new `CoreConfig.ready()`: its `create_profile` receiver has never been active and waking it would double-create profiles.

Tested end to end against a throwaway account inside a rolled-back transaction: weak login flags the profile, `/dashboard/` redirects to the warning, an API request is untouched, three skips increment and snooze correctly, the 4th login drops the skip button and a forced POST cannot push the counter past 3, change-password stays reachable, and setting a strong password clears both the flag and the counter. No account in production is flagged yet — flags only appear as people log in.
