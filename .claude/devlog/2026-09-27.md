# Dev Log — 2026-09-27

## 08:46 — Send To on a flow now follows the trigger

Building "Driver Approved → send WhatsApp" let you pick **Assigned Driver — WhatsApp**, which cannot work: that event carries no delivery task, so the flow saved fine and then failed on every run with *"No phone numbers resolved"* in its log, with nothing on the form to say why. Send To now scopes itself to the chosen trigger — options that cannot resolve are greyed out with the reason ("this event has no delivery task"), the picker lands on the most specific one that does work, and a line under it says what this trigger can reach. The save refuses a mismatch too, because a disabled option is a hint, not a lock.

New `core/auto_flow_triggers.py` is the single source: what each trigger hands the flow engine (a delivery task, an order, one person's phone, nothing at all, or — for the ~20 trigger rows nothing fires flows on — a red warning that a flow built on it will never run). The form options, the client-side scoping and the save check all read it, instead of the three drifting copies there were before. `core/tests_auto_flow_triggers.py` scans the source for every `execute_flows_for_trigger()` call and fails if a fired trigger is missing from the map.

Fixed three things the map exposed: `staff_order_create`, `staff_order_verify`, `wa_order_cancelled` and `staff_order_edit` never passed `order=`, so "message the customer when an order is created" resolved nobody; `business_cod_settled` carried only `business_phone`, which the "person this event is about" recipient does not read; and `business_unapproved_order` was missing from `TRIGGER_DOMAINS`, so it filed under Platform instead of Orders on the triggers page.

## 13:57 — A person event can now be sent to that person's WhatsApp number

Following on from this morning: on a driver trigger the only person option was "The driver this event is about", and it resolved `driver_phone`. But `driver_whatsapp` is its own field on Driver and is often not the line they take calls on — so a driver-approval message could land on a number with no WhatsApp on it. The person subject now offers **two** named options, "… — WhatsApp" and "… — Phone", and a WhatsApp flow lands on the WhatsApp one by default. The WhatsApp option falls back to the phone when the subject has no separate number, which is the case for every CRM lead.

That needed the number to exist in the event at all: `staff_driver_approved`, `staff_driver_rejected`, `staff_driver_suspended`, `staff_cod_settled` and `driver_application_submitted` now carry `driver_whatsapp`, and `business_cod_settled` carries `business_whatsapp`. The resolver reads `whatsapp` / `driver_whatsapp` / `lead_whatsapp` / `business_whatsapp` first, then falls through to the phone keys, and a blank-but-present WhatsApp field no longer swallows the phone behind it.

9 more tests, including the resolver picking the right one of a driver's two numbers. Verified on the live form: Driver Approved now opens on "The driver this event is about — WhatsApp".

## 15:55 — Unassigning a driver left the task reading "accepted"
When staff removed the driver from a task on the dashboard, the driver field cleared but the status stayed where it was. The unassign endpoint asked for 'pending' as a plain staff write, and staff status moves are forward-only, so the pre_save guard in delivery/signals.py silently reverted it — the task ended up driverless, still "accepted", in nobody's list and out of the driver pool (16 such rows in production). The state machine now recognises an `unassign` actor that may reset an open task to 'pending' (closed-out tasks are refused outright, so a delivered task keeps the driver its payout was built from), the client-facing status resets with it, and both the unassign and reassign endpoints now delete the stale `AssignedDriver` claim row — on its own that row still passed every driver-side ownership check, so the removed driver could keep working the task.

**Files:** `delivery/state_machine.py`, `workforce/views.py`, `delivery/tests_state_machine.py`, `workforce/tests_views.py`
