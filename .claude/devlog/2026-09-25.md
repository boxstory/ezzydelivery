
## 00:55 — Who pays the delivery charge, per client
Ops asked why "Delivery Fee Collected" showed 0.00 and wanted the driver's figure auto-filled
with COD + delivery charge. Checked the data first: of 400 real collections, 391 equal
`cod_amount` exactly and ZERO equal cod + charge, and `order.dl_amount` is set on 23 of 2002
orders. Drivers have never taken the fee at the door — it is invoiced to the client, and 448
tasks / QAR 9,640 were queued on that basis. So 0.00 was correct, and auto-filling globally
would have charged the customer for something the merchant is already billed for.

Agreed rule: a per-client switch. New `Business.customer_pays_delivery` (default False, i.e.
every existing account keeps today's behaviour). When ON, `delivery/collect.py` adds the
task's billable charge to the ONE figure the driver is shown; the split on the way back in
files it as `fee_collected_amount`, and `billable_tasks()` already drops the task, so the
client is never invoiced for a fee their customer paid. Never both.

An order marked `online_paid` asks for nothing at the door even with the flag on — whatever
the customer settled up front covered the whole thing, and asking again would charge twice.

The switch sits on Delivery App Control beside the proof and tracking rules, flowing through
`_apply_dac_rules` so the single-row and Save All paths cannot drift. Absent in a payload
means "leave it alone", the same convention `collect_dest` uses, so an older caller cannot
silently move who pays. The row summary spells it out, since it is the one rule on that page
that moves money.

Verified: flag OFF -> driver asked 300.00, client billed. Flag ON -> asked 325.00
(300 + 25), split back 300/25, client no longer billed. Online-paid + flag ON -> asked 0.00.

## 17:00 — Driver WhatsApp thread endpoint (blocked on a security decision)

Built the read half of "show the driver's WhatsApp history in the verification popup":
`driver_wa_thread` returns the last 60 days of stored WhatsAppMessage rows for a driver's
number, plus the URL and its core/departments.py entry. Factored the LID-safe identifier
logic out of `_lead_wa_identifiers` into `wa_identifiers_for(phone, override)` so the
driver side reuses the CRM rules rather than re-deriving them — a lid expanded as a phone
invents a real stranger's Qatar number, which is the whole reason that code is careful.

The endpoint works (proved against the 2,304-message thread for a busy number) but returns
zero rows for EVERY driver, by design and not by bug: `crm.services.wa_read_blocked` refuses
any number belonging to a platform account, and `platform_account_numbers()` is every phone
on every Profile — which every applicant has. So the gate is 100% coverage over drivers.

Stopped there rather than bypassing it. The gate exists because these threads carry our own
auth OTPs; there is a second defence (broad redaction at ingest, whatsapp/secrets.py), but
loosening a deliberate security control is the user's call, not mine. Popup left unchanged
so nothing is half-wired.

Also learned: every WhatsAppSenderRoute is on the Evolution channel, so a routed send does
not write a WhatsAppMessage row itself — but it sends from 97460003432, which WAHA is linked
to, so the outbound lands in the thread via WAHA ingest anyway.

## 17:20 — Return claims for goods we never delivered

Staff can now raise a return for a client whose own courier (or shop counter) put the parcel
with the customer — until today every return had to hang off an order we carried, because
`ReturnRequest.order` was a required FK and the collection service copied the address, charge
and item lines straight off that order. `order` is now nullable, and a standalone claim carries
its own collection address, drop-off location, charge and description; a set of `claim_*`
properties resolve either kind the same way so nothing downstream has to know which it is
holding. New staff form at `/workforce/returns/requests/new/` (OPS department), reached from a
button on the returns desk. From creation onwards it is an ordinary claim — the same Schedule
pickup button raises the same backwards-running collection order, which prices, routes, pays
the driver and stays silent to the customer exactly as before.

Also fixed on the way: `select_for_update()` on the claim now locks `of=('self',)` (two
nullable FKs made it an outer join, which PostgreSQL refuses to lock), the two staff endpoints
no longer write an order timeline entry against a null order, and the client's own returns list
and detail pages no longer reverse an order URL unconditionally. 32 new tests in
`orders/tests_standalone_return.py`; `orders`, `business.tests_replacement_client`,
`delivery.tests_pod`, `delivery.tests_exchange_leg` and the workforce returns suites are green
apart from the documented pre-existing `test_order_original_data_storage` failure.
