## 09:49 — Driver scanner: decode loop, label resolution, and an in-window next step
Three separate reasons a scan did nothing, all fixed. (1) The decode loop only ever started from the video's `loadeddata` event, which fires once — so after the first scan, `resetScanner()` re-registered a listener that never fired and scanning was dead until reload; it now runs its own timed loop (~8 looks/sec, cheaper on battery than the old every-frame `requestAnimationFrame` decode) and restarts cleanly. (2) The scan endpoint's third lookup filtered `OrderBarcode.barcode_value`, a field that does not exist — the FieldError surfaced to the driver as the error toast, so an unmatched scan never even reached its "no matching task" reply. Same broken filter fixed in `fleet_task_take_scan`. (3) The dashboard scanner only ever searched delivery tasks assigned to the driver, so a first-mile pickup label — the same label the Pickups tab scans happily — always failed; proved it by posting one order number to both endpoints.

Reworked the flow the way it was asked for: a scan now RESOLVES the label read-only via the new `/fleet/scan/resolve/` and shows the result in the scanner window itself — camera still running — with the steps that apply as buttons: Collect pickup (first-mile), Pick up from sender (own delivery task), Take this task (unclaimed pool). Nothing is written until the driver taps one. Warnings ("already collected", "another driver has this task", "nothing matches this label") render in the same panel instead of a toast that closes the view. The auto-closing 3-second success modal is gone. Camera failures no longer bounce to the dashboard — the message stays on screen with manual entry, which was itself unreachable under the overlay until this morning's fix.

Verified against production with a stubbed detector and a fake camera: a real pickup label resolved to two buttons (Collect pickup / Take this task) with business, customer and pickup location, and "Scan next" resumed detection (detect calls 3 -> 6). All three action endpoints were exercised with the exact payload the panel posts — all returned success — inside transactions that were rolled back, so no production row changed.
