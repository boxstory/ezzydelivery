## 00:20 — Client ledger: record a payment by hand (exchange-orders Phase 0)
First slice of the replacement/exchange-order work. Nothing in the system could record a client
*paying money in* — the client ledger was only ever written by the one-shot opening-balance route,
so an account was seeded once and then frozen. Added a finance-only "Record an entry" form on
/workforce/client-ledger/ that posts a payment, advance, credit, expense or adjustment; settlement
segments (COD, payout, delivery charge) are deliberately refused because their own legs post them

beside the balance: a narrower sum than the balance, covering only segments the account can actually
evidence, which is what a future door-step refund will be allowed to spend. Two new service
functions back it — `available_refund_credit()` and `mark_cleared()` for closing out a pending hold.

Fixed one unrelated thing found on the way: `driver_payout_invoice_columns` had shipped unclassified
in core/departments.py, so the fail-closed middleware was bouncing finance staff off the column
picker on a page they are allowed to use. That was breaking workforce.tests_departments.

Verified: 65/65 departments tests, 9 new ledger service tests, 11 new view tests, page renders 200
as staff with the rendered float matching the service, and the new route is live behind auth.

## 19:16 — Register page mangled non-Qatar business phones

The Contact Information block on /business/register/ only knew how to split a saved number when it
started with 974. Any other dial code (a UAE 971… number, for example) was dropped whole into the
"Business Phone" box while the Code box kept its 974 default, so the page silently recombined the two
into 974971…  — a 15-digit number that still passed the length check and would have been saved back
on the next submit. Replaced the hardcoded 974 test with the same COUNTRY_CODES splitter already used
in core/profile_add.html, longest code first, and made an unrecognised code fall back to a blank Code
box so recombining always returns exactly what was stored.

Also stopped the WhatsApp auto-fill from overwriting a WhatsApp number the business had already
saved: `waManuallyEdited` now starts true whenever the field arrives with a value, so auto-fill only
ever populates an empty field on first registration.

**Files:** `core/templates/core/business_register.html`

## 21:06 — Red error icon stuck on the register page's country-code box

The "+974" Code box on /business/register/ showed Bootstrap's red exclamation icon even when the
field was perfectly valid. Cause was the universal form-validation script in
templates/includes/scripts.html: it marks any input whose container holds a `.text-danger.small`
div as invalid, without checking whether that div actually says anything. The register page renders
two of those divs empty and `display:none`, as placeholders its own JS fills in later, so the marker
fired on page load every time and picked the first input in the column — the country-code box.

Added the missing check: an error div only marks its field when it has text and is not hidden, and
folded the two identical loops into one helper. Verified against fixtures that a real, visible Django
error still marks its field, and that an error inside a collapsed container still does too.

**Files:** `templates/includes/scripts.html`

## 22:07 — Fulfilment service was switched on for every client by a stray model default

The Services toggle on the seller page showed "Fulfilment service" ticked for clients who never
asked for it — Bex trading LLC (930072) among them. The page was honest; the database was wrong.
Migration 0010 had flipped `Business.fulfillment_service_enabled` to `default=True`, so every
business created since was born with fulfilment armed while its `fulfillment_service_status` stayed
at "Not Requested". 43 of 61 clients were in that state against only 9 genuinely active ones.

This was not cosmetic: a fulfilment-flagged client is refused SKU-less products by Product.save(),
is shown Warehouse/Inbound/Outbound menus it has no warehouse for, and gets bounced to the
add-products page when staff create an order. It also padded the "fulfilment-enabled" dropdowns on
the suppliers, warehouse-links and product-requests pages.

The default is back to False, and a data migration repaired the existing rows on evidence rather
than on the unreliable `fulfillment_activated_at` stamp (36 mis-flagged rows carry one equal to
created_at, and rows that were deliberately switched off keep theirs too). Clients with a real
warehouse footprint — an active link, stock on a shelf, or a product request — were promoted to
status "active": origeneral llc, Vénora trading perfumes and QCASEL. The other 40 were switched
off. The page now reads 12 active and 49 off, with no armed-but-not-onboarded rows left.

Two follow-on fixes. The Overview panel hard-coded a green "Active" badge behind the same single
flag, so it now reports the real status (Active / Requested / the status label in grey). And
`_retire_fulfilment_pickup_locations` decided whether a pickup row was a real warehouse by looking
for an *active* warehouse link — but every is_fulfilment_center row in the database carries a
warehouse_id, and none has a null one, so its "clear the stale flag" branch would have un-flagged a
genuine hub and put it back in the driver collection pool. The test is now whether a warehouse sits
behind the row at all. That caught Carty Qatar's "WH: EzzyDelivery FC- Sudan" row, which had lost
its link: it is deactivated instead of un-flagged, and their own shop address stays collectable.

Verified: 10/10 fulfilment-consolidation tests pass with both helper branches firing in the log;
32/32 across product/orders-inventory/seller-import; the seller page renders unticked for a disabled
client and ticked with a green badge for an active one. The 2 failures in `business warehouse`
(team-member access, order-update block) reproduce identically at HEAD in a worktree — pre-existing.
