## 05:14 — Driver application needs a location to submit; "Turn on location" banner on the Documents step
About 1 in 3 recent applicants (125 of 349 in 30 days) had no registration location, because a refused location never blocked the submit. The Documents step now opens with a "Turn on location to submit" banner and button. It goes green once a position is captured, red with phone-specific steps (Android, iPhone or desktop) when location is blocked or off, and takes the position without a tap when location is already allowed. Submit Application waits for it, and `join_driver` refuses a final submit with no location unless one is already on file. Save Progress and the step saves never need one. The banner only appears while no location is stored, so applicants editing later are not asked again. The old browser test asserting "denied location does not block the submission" now proves the reverse, plus recovery once location is allowed.

## 08:17 — "+ New label" in the chat panel
The inbox could only tick labels that already existed on a number, so a new label had to be made on the phone (and then took up to a day to appear, because of the 24h label cache). The label editor now has a "+ New label" row — name plus one of WhatsApp's 20 palette colours — behind a new `POST /waha/wa-chats/create-label/` gated to marketing and super admins, since a label belongs to the whole number rather than the chat it was made from. A name that already exists is handed back and simply ticked instead of creating a duplicate, and the created label is applied to the chat by the ordinary "Save to WhatsApp" so only one path writes to a chat. Two WhatsApp limits surfaced while testing live: a number holds at most 20 labels (the main number is already at that ceiling, so the endpoint says so instead of returning a bare 422), and WAHA cannot delete a label at all — its DELETE throws inside WhatsApp Web, while rename works.

## 17:34 — Driver application: location asked once, last, with no surprise prompts
Applicants found the Documents step confusing: it opened with a location banner, often already red with "tap the lock icon → Permissions" steps. The cause was that every step save (Save & Continue on steps 1–3) quietly triggered the browser's location prompt with no explanation. Applicants tapped "Block", and a blocked site can't be asked again, so step 4 could only offer phone-settings steps. Now step saves only take a position if location is already allowed (never prompting), the banner moved from the top of Documents to the bottom just above Submit ("Last step: turn on location"), it stays a plain ask on arrival even if the site is blocked, and the fix-it steps only appear after a tap fails. The instructions no longer mention a "lock icon", which current Chrome no longer shows. Two new browser tests pin the no-prompt and no-steps-on-arrival behaviour.

**Files:** `core/templates/core/join_us_driver.html`, `core/tests_driver_apply_e2e.py`

## 18:47 — Driver applicants get their CRM card when they save the form
A new driver applicant (MZB94) showed "No lead" in the WhatsApp inbox because driver cards were only built when someone opened the CRM driver board or the driver roster. The driver form now runs the same reconcile for just that applicant after every save that touches their driver row, so the card exists (or moves to the right column) straight away; a failure there is logged and never breaks the save. `reconcile_driver_leads` takes an optional `driver_ids`, prefetches `wa_links` (it was a query per unbound card), and runs under a Postgres advisory lock so the board, roster and form can't each create a card for the same new driver.

**Files:** `crm/services.py`, `core/views.py`, `crm/tests.py`, `core/tests_driver_apply.py`
