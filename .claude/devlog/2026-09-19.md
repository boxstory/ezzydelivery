# Dev Log — 2026-09-19

## 11:55 — CRM Leads section on the seller dossier (Details tab)
Added a "CRM Leads" section to the Details tab of /workforce/sellers/<id>/. It lists the CRM lead(s)
this client was converted from (stage, source, owner, created date) with a link through to each lead
card and to the full leads list. When no lead is attached, it instead shows the open business leads
that look like this client — ranked by the same phone/name matcher the business verification desk
uses (`_crm_suggest_leads`) — each with a Link button that posts to the existing
`crm_lead_link_business` endpoint, so a link made here marks the lead Won and is logged identically.

**Files:** `workforce/views.py`, `workforce/templates/workforce/seller_detail.html`, `workforce/static/workforce/css/workforce.css`, `templates/wf_dashboard_base.html`

## 12:20 — Sortable column headers on the CRM leads and Pricing Inquiries tables
Both staff tables can now be sorted by clicking a column header. Added a shared `workforce/sorting.py`
(whitelist per page, `?sort=key` / `?sort=-key`, blanks and NULLs always sink, ties break on -pk) and a
shared `_sort_th.html` header cell so other staff lists can reuse both. Stage and Pipeline sort in board /
pipeline order rather than alphabetically, and Orders/Mo ranks on the leading number of the band so 1000+
no longer lands between 1-25 and 101-300. Also fixed the filter bars on both pages: they posted to
`hx-get=""`, which htmx resolves to the current URL query string included, so every filter change
re-appended the whole filter set and the address bar grew a chain of repeated `search=&stage=&…`.

## 13:35 — Business Verification: two-line filter bar and six sort presets
Rebuilt the top of /workforce/verification/business/ as two lines instead of four. Line 1 is the status
buckets, line 2 is a single hairline bar holding search, the sort picker and the buttons — the old search
form was a Bootstrap flex row whose full-width input pushed its own button onto a second line. Sort moved
from three pills to a picker that applies on pick and now offers six readings of the queue: newest
applications, longest waiting, needs action first, newest/oldest accounts, business name A–Z. The default
view no longer opens on businesses that never applied (Postgres sorts NULLs first on a DESC, so every
never-applied row led the list). Every control in the bar now reads one height variable and meets the
staff-console floor (36px desktop, 44px phone).

## 14:27 — Web Push: staff can ask a driver in Waze to report in
Built the "ping the driver PWA" path that was scaffolded in sw.js but never
connected — nothing had ever called `pushManager.subscribe`, and there was no
VAPID key or send path on the server. Added a `DriverPushSubscription` model
(one row per browser endpoint, retired on 404/410), `fleet/push_service.py`,
subscribe/unsubscribe endpoints, an opt-in bar in the driver PWA, and an "Ask
for location" button in the live-map driver popup (ops-only, 2-minute cooldown
per driver). A push cannot read GPS — a service worker has no geolocation — so
the notification only brings the driver back to the app; `?locreq=1` on the
open makes `EzzyGPS.stamp()` take a fresh high-accuracy fix, which closes the
open nav handoff as usual. Verified against real FCM: our VAPID signature and
encrypted payload were accepted, only the fake device token was rejected (410).

## 14:41 — Dedupe the in-app row behind a location request
A failed push deliberately does not start the 2-minute cooldown (a transient
failure should be retryable at once), which meant a driver with notifications
off collected one "Location requested" row per press. `request_location` now
skips the write when an unread one from the same window already exists — one
standing request says everything a pile of them would.

**Files:** `fleet/push_service.py`, `fleet/tests_push.py`

## 17:07 — Add Order mobile view was missing five form fields
The phone view of /orders/add_order/ rendered its own markup separate from the desktop form, and it had drifted: latitude/longitude were display-only inputs with no `name` attribute, so any pin set by "Paste WhatsApp Location" or "Validate Address" was silently dropped on submit; `coords_accuracy` was absent entirely; the seller's own order number was a hidden field overwritten with a generated `ORD-<timestamp>`; COD status and the WhatsApp number were hidden auto-guesses with no way to correct them. Added a visible Order Number field (pre-filled with the view's suggestion, still auto-generating only if left blank), an editable WhatsApp field, a real COD Status select, gave lat/lng their field names, and wired `accuracyId` into the three address helpers so mobile records accuracy the same way desktop does. The auto-fill behaviour is kept but now stops overwriting once the seller edits the field. Verified by POSTing the mobile payload: all 24 form fields now round-trip to the saved order.

**Files:** `orders/templates/orders/order_add.html`, `business/static/business/css/business-mobile.css`
