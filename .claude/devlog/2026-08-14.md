# Dev Log — 2026-08-14

## 17:05 — WhatsApp OTP failover + honest password-reset errors

Password reset OTPs were silently not being delivered. The default Evolution instance
(`EzzyWhatspp` / 97466451589) is a zombie session — it reports `connectionState: open`
but every send and read returns "Connection Closed" (500 on send, 428 on read), and
`/instance/restart` did not revive it. `/instance/connect` refuses to issue a QR while
it believes it is connected, so re-linking needs a logout plus a QR scan on the handset.
Meanwhile the reset view swallowed the send failure with `except: pass` and still told
the user "a verification code has been sent", so the outage was invisible.

Added instance health tracking to `core/whatsapp_utils.py`: a failed send whose response
looks like a dead socket (428/500 or "Connection Closed") marks that instance down for
5 minutes in the shared database-backed cache (not the default LocMem cache, which is
private per gunicorn worker). Auth codes now go through `send_whatsapp_message_failover`,
which prefers the configured default number and falls through to any other connected
instance, so a reset still lands while the main number is down. A bad recipient (400)
deliberately does not mark the sender down. Ordinary routed notifications are unchanged.

The reset view now checks `whatsapp_auth_channel_down()` *before* the account lookup and
reports a real outage message when no instance can deliver — done before the lookup so
the response cannot be used to probe which numbers have accounts. Failed sends are logged
instead of discarded. Verified end to end: cold start fails over EzzyWhatspp →
Ezzy-COS (also disconnected) → Ezzy-Fleet and delivers.

Separately, two account issues on Shama Perfumes: the owner and the manager shared the
same WhatsApp number, and the reset view's `.first()` lookup resolved to the owner (lower
pk), so the manager's three reset attempts yesterday all targeted the wrong account.
Moved the owner's phone/whatsapp to his UAE number and set the manager's password
directly to unblock him.

**Files:** `core/whatsapp_utils.py`, `core/password_reset_views.py`

## 17:35 — Send health on the WhatsApp instances console

Staff had no way to see the outage above: the instances page renders Evolution's
`connectionState`, which reported `EzzyWhatspp` as "Connected" the whole time its socket
was dead. Instance health now records why and when a send failed (not just a boolean) and
the console shows a "Sending failed" badge that outranks Evolution's own claim, with the
error text and time, plus an explicit "Evolution still reports this number as connected —
re-link it" line for the zombie case. Reuses the existing `wai__st--bad` / `wai__note`
classes, so no CSS changes.

While verifying the badge, a probe send on `EzzyWhatspp` succeeded — the earlier
`/instance/restart` had worked after all, just several minutes later than the six
post-restart probes that all returned 428. Confirmed with a read op (data returned where
it was 428 before) and a real OTP send: auth codes are back on the default number
97466451589. The failover added earlier stays in place as the safety net.

**Files:** `core/whatsapp_utils.py`, `workforce/views.py`, `workforce/templates/workforce/whatsapp_instances_list.html`

## 17:50 — Per-instance send log behind a Logs button

Added a Logs button to the Actions column of the WhatsApp instances console. It opens a
collapsible row under the instance showing its last 5 send attempts — time, Sent/Failed,
masked recipient, and the error text with status code. This is the history behind the
"Sending failed" badge: the badge says a number is broken, the log says since when and why.

New `WhatsAppSendLog` model (core, migration 0025) records every Evolution send, success
or failure. It deliberately stores no message body — these rows cover OTP and password
reset sends and the console is a staff page — and the recipient is masked to 9746****545.
Rows are keyed by instance_name rather than a FK so history survives an instance being
deleted, and each write trims that instance's log to the newest 50. A logging failure is
caught so it can never take down the send it describes.

Bootstrap collapse rather than custom JS (the bundle is already loaded via
includes/scripts.html), and the panel is its own full-width row so opening it cannot
squeeze the columns above.
