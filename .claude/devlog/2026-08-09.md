# Dev Log — 2026-08-09

## 11:25 — Return-to-hub: destination resolver service (Phase 1 start)
Planned the driver parcel-custody / return-to-hub feature after failed or postponed deliveries, and
built the first piece: a service that decides where an undelivered parcel physically goes back to.
The key finding behind the plan is that `failed` is a terminal status and nothing in the system
records that the driver is still holding the goods — `cod_in_hand` tracks cash only, and the only
existing handover is outbound (warehouse → driver). There are currently 251 failed delivery tasks
with no custody record at all.

The resolver prefers the hub the parcel actually came from (leg-2 hub, then the leg-1 batch, then the
first-mile drop point, then the business's linked warehouse) instead of the single global default
that `resolve_default_hub()` returns, and supports sending a return back to the merchant's pickup
location when the business is configured that way — falling back to the hub with a recorded reason
when that location is suspended, pending, or is itself a fulfilment centre. All four branches were
exercised read-only against real production rows. Also defined the custody status list and a history
logger that writes into `OrderStatusHistory` (with `old_display`/`new_display` populated, since
`new_display` is not nullable).

Not yet built: the `ParcelCustody` / `ReturnHandover` models, the signal that opens custody, the
driver PWA return tab, and the hub receipt console. An adversarial review council is still running
against the plan before those land.
