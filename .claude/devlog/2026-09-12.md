## 01:35 — Fix the dead dl_to_address FK (driver area filter returned nothing)
DeliveryTask carries two FKs to the same DlAddressUpdate model. `dl_address_update`
was set on all 1781 rows; `dl_to_address` was NULL on all 1781 — yet ~168 read
sites go through `dl_to_address` and only ~24 through `dl_address_update`. The
consequence was bigger than the dead write I originally reported: the driver PWA's
Area filter (Doha / My Zone / Qatar) filters purely on `dl_to_address__dl_zone`, so
**every driver picking any of those three saw zero tasks**, and the zone dropdown
was empty. Card fields with no order-level fallback (unit, area, property type,
time slot) rendered blank too.

Three-part fix. Migration 0050 backfills `dl_to_address` from `dl_address_update`
(1781 rows, both FKs now agree on every row). `delivery.signals.delivery_task_pre_save`
mirrors whichever FK is set onto the other so new rows cannot drift — placed above
the status guards in that function, which return early. And a shared
`delivery.selectors.task_address(task)` resolves the address with a fallback chain
(dl_address_update → dl_to_address → dl_task_number match) for rows written by
bulk_create/queryset.update(), which skip pre_save; the two AI-address-parse blocks
in `workforce/views.py` and `orders/views.py` now go through it instead of reading
the always-NULL field.

Measured after: area=doha 0 -> 532 tasks, area=qatar 0 -> 1101, zone dropdown 0 -> 91
distinct zones; for the busiest driver, 328 Doha / 701 Qatar out of 1115 published.
Mirror verified by clearing the FK on a row and re-saving.

Honest limit: the FK fix only makes reachable what is actually stored. Of 1794
address rows — zone 91%, street 65%, building 69%, name 100%, mobile 99%, real GPS
90%, but area_name 2.7% and dl_unit / time_slot / property-type 0%. Those last four
are never written by the auto-creation in orders/signals.py, so those card fields
stay blank; that is a data-capture gap, not this FK bug.

Test run: 454 tests across `delivery` + `fleet` + `orders.test_warehouse_inventory`,
4 failures. None are from this change — 3 are `WarehouseInventoryAdjustmentTest`
(inventory not adjusting on task status change) and reproduce identically with the
pre_save mirror hunk temporarily removed; the 4th is the pickup date-range test
already noted at 00:37. Both sets belong to the branch's other uncommitted work.

## 02:55 — Warehouse inventory moves at pickup, not delivery
Three `WarehouseInventoryAdjustmentTest` failures turned out to be a feature the
tests specified and nobody had built: a task-level stock movement. The handler only
acted on `delivered` (deduct) and `failed` (return), so between the driver
collecting the goods and the customer signing, the units were counted as on-hand
while physically on a motorbike. Added `ship_stock_for_task` / `return_stock_for_task`
in warehouse/signals.py — goods leave the shelf at `picked_up`, come back on
`failed`, and `delivered` now moves no stock when the pickup already shipped it
(falling back to the legacy order-level fulfil for flows that skip picked_up, e.g.
to_review → publish → delivered, so those are not left on the books). Rows are
tagged `reference_type='delivery_task'` to keep them distinct from the order-level
reservation path, and that tag is the idempotency key: a status that revisits
`picked_up` after a correction must not deduct twice.

One test assertion was wrong and I changed it: it expected a positive `quantity` on
a ship row, but `InventoryTransaction.quantity` is a signed delta everywhere else in
the module (ship negative, return/receive positive, `quantity_after -
quantity_before == quantity`). Honouring the test would have made this one path
break that invariant and left the ledger un-summable. Asserted the invariant
explicitly instead. Added 3 regression tests: status bounce deducts once, double
`failed` returns once, delivered-without-pickup still deducts. 8/8 pass.

## 03:05 — Address rows inherit area name and time slot from the order
`DlAddressUpdate.area_name` sat at 2.7% and `time_slot` at 0% while the same data
was already on the Order — `delivery_area_name` 65.3%, `preferred_time_slot` 3.1%.
Nothing copied it across. Creation in orders/signals.py now sets both, and because
`delivery_area_name` is resolved from the pin *after* the row exists
(delivery.geo.apply_delivery_area), the receiver also fills blanks on later saves —
blanks only, so a hand-typed area is never overwritten. Migration 0051 backfills:
area_name 2.7% → 66.1%, time_slot 0% → 3.1% (which is all the order data there is).
Also replaced `order_number not in queryset.values_list(...)` with `.exists()` on the
line above — it was pulling every address row's number into Python on each save.

Correction, found by a test I wrote for the change: the first version of the
blank-fill sat inside the receiver's `if created:` branch, so it could only ever run
on creation — useless for the case it was written for, since the pin (and therefore
the area) usually arrives on a later save. The backfill had masked it. Moved into
`_refresh_delivery_area`, which is where the area is actually resolved and which
runs on every save. A second mistake in the same edit put the block inside
`_resolve_zone_number` referencing an undefined `instance`; caught by reading the
file back before reloading, so it never reached the running server.

`dl_unit` and the villa/flat/office flags stay at 0%: no field on Order holds them
and the customer page only renders them read-only, so nothing in the system captures
them. `DlAddressUpdateForm` is now unused and has exactly those fields — it is the
natural basis for a capture form on the tokenised address page, but that is a new
flow, not a bug fix, so I left it and noted it in the module docstring.

## 22:46 — Django comment trap: three templates were printing their own comments

`{# ... #}` only works on a single line — Django treats a multi-line one as literal
text and renders it. Three templates had two-line `{# #}` blocks, so the explanatory
comment was printing onto the live page: next to the status badge in the staff pickup
pool, on the driver PWA task card under the office-note strip, and above the "Note to
Driver" button on the staff task detail page. All three converted to
`{% comment %}` / `{% endcomment %}` blocks; a project-wide scan now finds zero
remaining multi-line `{# #}` comments.

**Files:** `workforce/templates/workforce/pickup_pool_status.html`, `fleet/templates/fleet/driver_tasks_pwa.html`, `workforce/templates/workforce/parts/delivery_task_detail.html`
