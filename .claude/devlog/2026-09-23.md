## 10:03 — Gap-test the return pickup end to end, and fix what it found
Walked a collection through the real driver and staff endpoints rather than reasoning about
the code — staff schedule, driver takes it from the pool, start ride, complete — and probed
the failure, cancel, empty-claim and two-claims paths. Three genuine gaps came out of it.

The claim never moved: a driver could collect the goods and hand them to the seller while the
return request still read "Pickup Scheduled" forever. It now follows the task, the same way a
return leg's custody row does — picked up at the door, received when it reaches the seller —
and only ever forwards, with a decision made by hand (rejected/closed/refunded) outranking the
van. Closing a collection as returned-to-shipper raised a return request against the
collection order itself, which staff could then schedule another collection for; that is
refused now, because a collection that comes back is the same goods still at the customer's.
And a cancelled collection left the claim stuck forever, since the link to it blocked a second
attempt — staff can now re-schedule, and the new order gets a fresh -RP2 code instead of
colliding with the abandoned one.

Two things the probe cleared rather than condemned: the task does appear in the driver PWA
(under the pool tab and on the map — an earlier read was checking the wrong tab), and the
driver's earnings sitting at None right after delivery is normal for every leg, since that
column is filled by the payout desk. 13 more tests, including a silence test with a positive
control proving an ordinary delivery still messages the customer while a collection does not.
222 tests across orders/delivery/warehouse and 26 across delivery/fleet pass.

## 11:26 — Every return and replacement movement is now its own task
A collect-back replacement used to be one visit with a flag on it: the driver was told to
"bring the original back" and nothing modelled where those goods went — no destination, no
custody row, no record that he was carrying a seller's stock home. That flag no longer makes
an exchange leg. The outbound replacement is an ordinary drop, and when it reaches the
customer a collection task is raised for the original items with two real ends: collect at the
customer's door, drop wherever that client's goods go.

Where they go is a new field, `Business.return_collection_destination`, defaulting to the
client's own counter. It is deliberately NOT the existing `return_destination`: that one
answers a different question — where a parcel we failed to deliver goes — every client sits on
its untouched 'hub' default, and routing collections off it would have redirected every failed
delivery in the system to merchants' shops. Staff set the new one on the Delivery App Control
page beside the proof rules. A collection routed to a hub stamps the hub on the task, opens a
custody row as the driver collects, and lands as received/hub when he drops it — which is
exactly what the returns console's forward queue looks for, so the run back out to the client
is raised by the button that already handles every other parcel on our shelf.

The exchange leg keeps its fee branches and its banner for tasks already on the road; nothing
new is born with it. Drivers get a collection banner naming both ends, and dispatch gets a
Collection flag in the task list. Two tests encoded the old contract and were rewritten to the
new one rather than deleted.

Verified by walking it: replacement delivered → collection raised → ends correct → hub route →
custody received → forward leg raised. 16 new collect-back tests, 6 new console tests. 335
tests across orders+delivery and 259 across business come back to exactly the 8 known
failures; warehouse, workforce returns and fleet map suites green. All 63 clients confirmed on
'business' for collections with 'hub' for undelivered — unchanged behaviour on both counts.

## 18:45 — A returned delivery is now a real, billable, payable job
Until now a parcel that went out and came back was invisible to the money side: the
order stayed at whatever status it had (2385 sat on "Published"), the task never reached
Client Charges, and the driver who drove the whole trip was never paid for it.

Three changes, per the rules agreed with ops:
1. **Order status** — added a `returned` choice and `_sync_order_status` now sets it on
   `returned_to_shipper`. The existing terminal-status guard means an order that was
   genuinely delivered and only later returned for alteration (2374) keeps its delivery,
   its `delivered_at` and its charge. `returned` was added to all three
   TERMINAL_ORDER_STATUSES lists so it does not leave a claimable pickup behind, and
   cancel is blocked for it in the view and the template.
2. **Client charge** — `BILLABLE_STATUSES` now includes `returned_to_shipper`, so the
   full delivery charge bills automatically. The Client Charges console and the driver
   payout queue both read that one constant now instead of keeping their own copies.
   The invoice line reads "Returned delivery <ref>", never "Delivery".
3. **Driver pay** — the returned trip enters the payout queue and proposes `normal_fee`,
   the same as a drop. No change to earnings.py was needed; a `single` leg already falls
   through to the normal fee.

The run back out to the client keeps its own charge: 0 when raised the same day (the
client is already paying for that journey) and the outward rate on any later day, since
it then costs a second driver and a second trip.

Backfilled: order 2385 → Returned. Two returned tasks now bill QAR 35 + 25 to Alan the
label and propose QAR 10 each to their drivers.
