## 21:45 — Client accounting ledger: the account table and its service
Built the spine of the per-client ledger. `BusinessLedgerEntry` (fleet migration 0040, applied) is an append-only account: one row per money event carrying segment, status, billing state, debit/credit, the related order/task/driver/transaction/invoice, and denormalised order and task numbers so the table renders without joins. Balance means what EzzyDelivery owes the client; negative means they owe us. Two database check constraints enforce that a row is single-sided and non-negative — verified by trying to insert bad rows, which Postgres rejects.

`fleet/ledger_service.py` is the only writer: `post`, `reverse` (a contra entry that leaves both rows visible rather than deleting), `post_opening_balance`, plus `balance`, `entries` and `segment_summary` for reading. The running balance is a correlated subquery, deliberately not a window function: a window is evaluated after WHERE, so filtering the ledger to one segment would silently restate the balance column as a running total of just the filtered rows. There is a test proving the advance row still reads 525.00 under a segment filter rather than -200.00.

Opening balance seeds only what is already documented — COD we hold, less unpaid invoice balances — and deliberately excludes charges not yet on an invoice, which would otherwise be billed once on the opening figure and again when an invoice is issued. Dry-run against production showed one account holding 35,375 QAR of COD seeding correctly. 13 new tests; the 41 existing payout/billing tests still pass.

Also fixed while cloning it: the code-generation retry loop caught any IntegrityError and immediately queried again on a transaction Postgres had already marked broken, burying the real cause. The ledger's version uses a per-attempt savepoint and only retries an actual duplicate code. `BusinessChargeInvoice.save()` still has the original flaw — harmless today because it has no check constraints, but noted.

## 22:35 — Client Ledger screen, and its sidebar entry under Finance ▸ Seller
Put a face on the ledger built earlier. `/workforce/client-ledger/` opens on an account picker and shows nothing until a client is chosen — a running balance across accounts would be meaningless, so a cross-client view could not carry the Balance column at all. Once an account is open the page shows a navy balance headline that states the direction in words ("EzzyDelivery owes X" / "X owes EzzyDelivery") rather than making staff read a minus sign, a card per segment with its total and what has not cleared, and the accounting table: Date, Entry, Segment, Order/Task, Description, Status, Debit, Credit, Balance. Filters for segment, status, direction, date range and a free-text find over order/task/entry codes, plus CSV export. An account with no opening balance gets a prompt to post one.

Sidebar link added under Finance ▸ Seller in the desktop and mobile sidebars, with the URL pattern registered in the desktop sidebar's active-menu JS map. Both new URL names were classified into the finance department in `core/departments.py` — `/workforce/` fails closed, so an unclassified route would have 403'd; `workforce.tests_departments` (65 tests) passes.

Two things caught by loading the page rather than assuming: the account dropdown did not preselect the account the page was showing, because the list was active-businesses-only and the account in question is suspended. Most sellers here sit at 'pending' and a suspended one can still be holding thousands in COD, so the list now covers active accounts plus any with a ledger, held COD, or a live invoice, plus always the selected one. Also fixed a stray corrupted character in the page's JS block.
