## 10:17 — Zero COD is a COD: ledger row + correct display
A delivered order with 0 QAR COD was being treated as if it had no COD at all. The driver still goes through the collection step and confirms zero, but ezzy_api marked the task collected only when the amount was above zero, so the task page showed a delivered job as "Pending Collection" forever and no wallet transaction was ever written. Added a resolved COD state in the workforce view (a zero-amount COD on a delivered task counts as collected, falling back to the driver's COD activity log for the timestamp) and switched the COD highlight badge, the COD status/amount fields and the new timeline COD event over to it, so a 0 QAR collection is shown as a real collection with its amount and payment method.

On the backend, both delivery-completion paths now write a 0 QAR cod_collection transaction for zero-COD orders, idempotently, so staff have a ledger row to attach the delivery fee to when billing the client. The stored cod_collected flag is deliberately left False because the driver settlement pages count zero-COD deliveries separately through that flag; to keep those counts honest, zero-amount rows are excluded from the ledger's per-method order counts. Added a backfill command for the 235 historical zero-COD deliveries that have no transaction — dry run only so far, not yet applied.

## 11:09 — Fix: driver PWA camera scanner blocked by Permissions-Policy header

Verified live: the header now reads `camera=(self)` on ezzydelivery.qa.
