## 10:07 — Fix the pickup GPS-coverage badge reporting "No GPS recorded" on legs that had GPS
The first-mile GPS badge claimed no location corroboration on legs where the driver's phone had been reporting the whole time. Two causes: it counted pings inside `accepted_at → close`, but the median leg on this database is 7 seconds wide (86% under a minute) because accept and close happen in the same interaction, and the PWA only pings about every 30s — a window that short structurally cannot contain a fix. ## 11:05 — Stop storing the same GPS fix several times
The GPS badge on pickup 127 read "377 fixes" for a leg that held only 86 distinct positions. The driver PWA re-sends whatever `getCurrentPosition` hands back, and with `maximumAge` set that is routinely the same cached fix — the duty cycle restarts itself on a profile change and asks again, the error path deliberately re-reports the last known position, and every open PWA page runs its own sender. The ingest bulk-created all of them with no uniqueness check, so one driver's 3,000 rows held 821 distinct fixes and every count over the table read ~3.6x high. Fixed on three levels: the ingest now drops a ping repeating a stored `(fixed_at, lat, lng)` for that driver and answers 200 "already recorded" (a 4xx would send the offline queue chasing it forever); the PWA skips a fix identical to the one it last sent, saving a request with no battery change; and the pickup badge counts distinct positions rather than rows so the 8,833 already-duplicated rows (30% of the table) read correctly without deleting anything. 127 now reads 86 fixes, 150 reads 7 instead of 21.

**Files:** `ezzy_api/views.py`, `fleet/templates/fleet/pwa_base.html`, `workforce/views.py`

## 14:12 — Delivery area persisted on Order instead of resolved per page load
The neighbourhood shown under the zone name on driver task cards was being resolved live on every page render and thrown away, so only that one view could see it. It is now stored on the order as `delivery_area_name` plus a `delivery_area_source` recording how it was reached (nearest area to the pin / only area in the zone / suppressed as a duplicate of the zone name / unresolved). The resolver moved into `delivery/geo.py` beside the route-distance code, reads a cached zone-area map, and is kept current by a new `_refresh_delivery_area` hook on the Order post_save signal — a queryset update, so it lands even when a caller saves with `update_fields`. A `backfill_delivery_area` command filled the 1489 existing orders (977 by pin, 476 suppressed duplicates, 36 unresolved) and is idempotent: a second run reports 0. The driver view lost its inline block and now issues zero ZoneArea queries.

Two pre-existing bugs fixed while in the same lines: the route-distance signal's `.update()` never persisted `route_distance_source`, and `invalidate_zone_cache()` never cleared the zone-centre map, so a zone pin edit left every zone-estimate distance stale for an hour.
