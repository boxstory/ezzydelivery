# Dev Log — 2026-09-01

## 00:08 — Seller Transactions: select across all pages, trimmed selection bar
The selection bar on the seller COD ledger now reaches past the visible page. Ticking every row on a page offers "Select all N across every page", which pulls the whole filtered set from a new `rows=json` branch in the view (capped at 5000 rows) and holds the picks in sessionStorage keyed by the seller plus the active filters — so selection also survives paging and re-sorting instead of resetting each time. Export builds its CSV from that store, and Print adds print-only rows for picks made on pages that are no longer on screen.

Bar itself was trimmed at the user's direction: the "Copy codes" button is gone, and the remaining actions read "Export" and "Print" rather than "Export selected" / "Print selected". Verified as staff: the JSON branch returns all 182 matching orders for seller 781706 (page size 50), the page renders the new control, and the served CSS carries the new `ftr__bulk-scope` / `ftr__row--printonly` rules.

## 00:26 — Client Charges: Delivered column + sortable table headers
Added a "Delivered" column to the Client Charges ledger showing `completed_at` (date on the first line, Qatar-time clock beneath) and split the old blended date cell into a plain "Task Date" from `dl_task_date` — the two only agree when a job is completed on the day it was booked, and the charge is judged against the delivered one. Made eight thead columns click-to-sort (Task, Business, Task Date, Delivered, Service, Calculated, Verified, Status): each header is a link carrying the current filters and status cut, clicking the active column reverses it, and the glyph shows idle vs asc vs desc. Sorting is server-side because the table is paginated; `completed_at` orders with `nulls_last` so undated rows no longer float to the top of the newest-first view. The Sort dropdown now renders an extra "Column sort" option when a header picked an order outside its five presets, so re-submitting the filter form no longer silently resets it.

## 16:20 — Unapproved businesses gated to read-only

Investigated how "SHAMA PERFUMES" appeared as a live business without staff approval. No breach:
the self-service signup at `core.business_register` creates the Business row with
`business_status='pending'` on the plain Save button, and nothing downstream ever checked that
status — `business_required` grants full owner access on the row's mere existence, and the write
gate only ever blocked `'suspended'`. The client walked into the dashboard, created a pickup
location and a real order that reached the fleet queue, entirely unseen by ops.

Widened `business/suspension.py` from a suspension-only gate to `WRITE_BLOCKED_STATUSES =
('suspended', 'pending')`, with separate reason codes so a pending account gets "awaiting
approval" wording instead of "suspended". `'inactive'` deliberately stays writable. Also found
that the gate was barely wired into `business/views.py` at all — only the Shopify/API views and
returns had it — so pickup locations, team invites, driver directory, WhatsApp triggers and
branded tracking were open even to *suspended* businesses; added the decorator to 15 write views.
A client's own profile/logo edits stay open so they can fix details staff ask them to correct.

Added an ops alert (`business_unapproved_order` auto-trigger + warning log) that fires if an order
is ever created for a non-active business, as a backstop behind the gate. Fixed two adjacent bugs
found on the way: the staff dashboard's seller tiles counted `'Approved'`/`'Pending on Review'`,
which are not valid statuses, so both read 0 forever; and `core.business_profile_update` let a team
member reassign the owner's business to themselves, and additionally 500'd on every successful save
by reversing a URL with an argument it does not take.

Test fixtures in `tests_suspension.py` had no pickup location, so `add_order` redirected for an
unrelated reason and two assertions there had been passing/failing vacuously — two were already
failing at HEAD. Fixed the fixture so the assertions test the gate. 39/39 pass.

## 17:40 — Order renumbered to SMP102-5362-AB601

Renumbered order 2135 off the deleted business's prefix. The string was carried in seven
places, not one: `Order.order_number`, `DeliveryTask.dl_task_number` + `dl_task_description`,
`OrderBarcode.order_number` (plus its QR image), `ShippingLabel.label_number` + `barcode_data`,
`DlAddressUpdate.dl_task_number`, and `DeliveryTaskQRCode.task_number` + its QR image. A
full-table text sweep across every CharField/TextField in the project found the last two after
the obvious ones were done.

templates already render `#{{ order.order_number }}`, so storing the hash would display

own order code, never as a prefix.

Both QR images were re-rendered (their `save()` hooks only auto-generate when the field is
empty, so `DeliveryTaskQRCode.generate_qrcode()` had to be called explicitly) and verified by
re-rendering a reference QR of the expected payload and comparing pixels — they genuinely decode
to the new number. The shipping label was rebuilt rather than patched, because it still carried
the deleted business as sender ("SHAMA PERFUMES / GEWAN ISLAN / 97433192868") and a
`LBL-None-` prefix from that account's missing business_code; it now reads
`LBL-SMP102-SMP102-5362-AB601-F88412` with the Pearl Qatar sender. `original_order_data` was
deliberately left on the old number — it is the "original data as proof" record.

Three orphaned media files removed (two old QR pngs and the old label image) after confirming
no DB row referenced them; copies kept in the session scratchpad.
