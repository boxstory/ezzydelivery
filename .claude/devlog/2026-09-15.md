## 15:56 — Custom-API storefront orders now land in the Temp Orders list
Gooey's orders were nowhere to be found because the custom store API (`/api/v1/store/orders/`) created a live Order directly and `TempOrder` had no `custom_api` source type at all — so the Temp Orders page could never show them. Changed the endpoint to stage the checkout as `TempOrder(source_type='custom_api')` instead, which puts custom-API sellers in the same review queue as OneDrive, Google Sheet and webhook sellers; staff Import / Auto-import is now what creates the Order. The POST response keeps its shape but carries `order_number: null` and `order_status: 'received'` until the row is imported, and the status GET answers from the staged row instead of 404ing while a storefront polls.

Care was needed at two seams. COD: both import paths derive `cod_status_by_client` from `TempOrder.financial_status`, so prepaid checkouts stage as `financial_status='paid'` with `cod_amount='0'` — otherwise an ApplePay order would import as COD and the driver would ask the customer to pay twice. Basket: the importer rebuilds OrderItems from `raw_row['product_N']/['count_N']`, so those pairs plus `package_qty` are written alongside the full payload — gooey maps `package_desc` to bare item names, so without them "S'more x2" would have imported as one unit and no line items.

Also: `sync_all_temp_orders` now names the push sources explicitly (asking it to sync `custom_api`/`webhook` returns a note instead of a silent zero), refetch treats pushed rows as a no-op rather than a red "refetch failed" on every auto-import, and the Temp Orders page gained source filter options and row badges for Custom API and Webhook (both were missing). Verified end to end against production with two throwaway orders — they appeared on the page under the gooey group and were deleted afterwards. 28/28 store-API tests pass, including the transfer-to-Order tests for COD, prepaid and basket contents.

## 16:10 — Pull orders from a seller's own REST API
Custom storefront integrations were inbound only: the seller's site POSTed to `/api/v1/store/orders/` and we never called them. Added the opposite direction — a `custom` integration row can now carry a fetch URL plus the API key the seller's own site issues us, and we GET their orders on the hourly `sync_temp_orders` cron and from the Temp Orders "Sync" button. Kept it on the same row and the same `column_mapping` rather than inventing a second platform type, because the JSON shape is identical whichever way the order travelled.

The push endpoint's staging logic was extracted into `stage_order_payload()` so both legs create rows the same way; that also gives the pull idempotency for free, which is what stops an hourly re-read of the same open-orders list creating a duplicate delivery every hour. Outbound calls are SSRF-guarded (the URL is merchant-supplied and called on a schedule with a credential attached), redirects are refused, and the response is capped at 8MB / 200 orders. Client and staff API test pages now actually call the endpoint and report the count, or explain that the integration is push-only. 32 new tests; the 28 existing push tests still pass.

## 21:07 — Custom API: staff fields, order/product fetch buttons, no guessing
Three gaps closed on the custom-API integration, all driven by making it reusable for any client rather than fitted to one.

The staff integration modal had none of the pull fields, so a staff member could not configure or even see a pull integration — everything I added earlier was only reachable from the client-side form. Added the full set (fetch URL, auth style, header/param name, their key, list path, status field, status filter, product URL, product list path, auto-pull toggle) plus product field paths, wired through the get/create/update endpoints. Two traps fixed along the way: the new columns are NOT NULL with a `''` default while the older credential columns are nullable, and the modal coerced every blank to `None` which would have raised IntegrityError; and an unticked checkbox posts nothing, so auto-pull could never be switched off until the modal started posting it explicitly as 1/0.

The seller page's Orders tab only knew Shopify/WooCommerce, so a pull integration showed "No Shopify or WooCommerce API configured". It now fetches from the seller's own API, deliberately without applying the status filter, so staff can see the order that is being skipped and why rather than it being silently absent; each row says whether it is in Temp Orders or already an Order. The Products tab got the same treatment behind a separate product URL, since an order feed says nothing about a catalogue — sellers with orders only now get told that instead of seeing a dead button.

Finally, removed the guessing. A custom integration now resolves every field through its configured mapping and nothing else: no falling back to likely-looking key names. A guessed SKU silently merges two products and a guessed price is charged to a customer, so an unmapped field stays visibly blank and the UI names what is missing. Product fetch reuses the same credential and all the same guards (SSRF, no redirects, timeout, byte and count caps) via a shared transport. 57 pull tests pass.

## 21:28 — One server-side definition of which fields each platform uses
Selecting "Custom" still showed the platform credential boxes (API Key, Secret, Access Token, API Version) even though a custom integration authenticates against the seller's own API with the key their site issued us — those boxes are where a merchant pastes the wrong key. Custom now shows only its own twelve fields.

The bigger fix is where that list lives. It was hardcoded twice: a `FIELD_CONFIG` literal in `api_form_fields.js` for the client form, and `data-show-for="..."` attributes on 31 groups in the staff modal. That duplication is exactly why the modal was missing every field added earlier today. Both now render from `business/integration_fields.py`, handed to the page via `|json_script` and read by each UI; the modal's groups declare `data-field="<name>"` and the map decides visibility. No field list remains in any JS file or template — verified by grep. Conditional visibility (the header/parameter name only applies to the header and query auth styles) moved into the map too, so neither UI carries the rule.

One trap: `|json_script` encodes whatever it is given, so passing the pre-encoded JSON string double-encoded it and the browser parsed it back to a string. The views pass `as_dict()`; `as_json()` stays for callers that embed it themselves. Added a test asserting every field named in the map actually exists on BusinessApiSettings, since a typo there would silently hide a field in both UIs. 62 pull tests pass.
