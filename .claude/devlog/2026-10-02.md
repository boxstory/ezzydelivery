## 16:08 — Per-connection "Import Qatar orders only" filter
JM AUTO PARTS' Shopify store sells across the GCC: all 11 of its live orders ship to UAE,
Bahrain or Pakistan, and the hourly cron had already staged all 11 as importable. Added an
opt-in checkbox per API connection rather than a blanket rule, so no existing seller changes
behaviour. Default OFF on all 11 connections; the seller or ops ticks it per store.

Shopify cannot do this filtering for us — its GraphQL `query:` silently ignores an unknown
field, so `shipping_address.country_code:QA` returns every order, identical to a nonsense
control term. Verified live, hence a client-side rule in `core/destination.py`. An order counts
as Qatar when shipping_address country is QA, or the phone is a Qatari 8-digit 3/5/6/7 number.
Billing is ignored on purpose (live order #1001 ships to Pakistan but bills to the UAE). Reads
all four shapes the import paths hand it: raw Shopify dict, shopify-lib object, staged row dict
and WooCommerce dict. An order with no country AND no phone is kept, not hidden — a wrongly
hidden Qatar order is never delivered and nobody finds out.

Foreign orders are staged as `status='skipped'` (a choice that existed but was dead) with a
`_skip_reason` on raw_row, never deleted, so "why is order X missing?" stays answerable on the
Temp Orders page. Wired into the staging cron, the merchant import page, the quick HTMX panel,
the staff importer (both Shopify and Woo branches, refusing with a reason since staff pick ids
by hand) and the unattended AI-agent import. Deliberately NOT wired into the connection-test,
preview or export fetches: for this client every sample order is foreign, so filtering there
would make a healthy connection report "no orders".

Verified end-to-end against the live store inside a rolled-back transaction: 11 of 11 withheld,
0 importable. 23 new tests; `business` suite shows the same 7 failures as a HEAD worktree
baseline, so no regression.

## 18:16 — Guards so a Shopify connection cannot fail silently again
JM AUTO PARTS failed twice for two different reasons, and only the second (a custom domain)
was guarded earlier today. Closed the remaining three holes, all at save time so a merchant
is told what to fix instead of being sent to an unexplained Shopify error page.

Added a pre-flight Client ID check: POST a deliberately invalid code to the token endpoint
before accepting the credentials. Shopify validates the application before the code, so
`application_cannot_be_found` identifies a Client ID that is not an OAuth app — almost always
the API key of a Custom App created under Develop apps. It fails OPEN on any network error so a
blip never blocks good credentials. Verified against all six live Shopify stores: the five
working ones are accepted, the key that originally failed is refused.

The Client SECRET cannot be checked this way — Shopify rejects the bad code before reading the
secret (confirmed live: a real secret, a wrong secret and a secret equal to the Client ID all
return the same `invalid_request`). So the secret is validated by shape instead: refused when it
equals the Client ID, or when it is a 32-hex string (an API key pasted into the secret box).

Fixed a silent bug this exposed: the OAuth callback set `is_verify_api` but never `is_default`,
while the order import requires both. It now adopts the default only when the business has none,
never stealing one the seller chose. This had already stranded a live client — Vénora trading
perfume is active with a valid token but no default, so their import reports "No store
integration is connected". Their row is NOT changed here; flagged for a decision.

Also refused a duplicate connection for the same store (checked in the add view, where the
business is actually attached), after a double-submit created two identical rows 14s apart.

The pre-flight check found a second casualty: Noorain abayas, active, connection created
2026-08-01, has a real shpss_ secret but no token and an unrecognised Client ID — the same
failure, sitting unnoticed for two months.
