# Dev Log — 2026-08-04

## 18:05 — Multi-number support on WAHA (marketing + operations on one container)

Made the whole WhatsApp stack session-aware so a second WhatsApp number can run
alongside the existing one. The blocker recorded yesterday ("this WAHA is CORE
tier, which is single-session") is stale — the running container is 2026.7.1,
and WAHA folded unlimited sessions into free Core at 2026.6.1, so one container
hosts both numbers. Two containers were considered and rejected: the routing
model (`WhatsAppInstance.waha_session`) already keys on a session name, so a
second container would mean per-instance base URLs, a second API key, a second
nginx block and a second webhook secret for no extra capability.

The real work was Django, not Docker. `WhatsAppMessage.session` existed but was
never read — every query was session-blind, so a second number would have
silently corrupted data. Biggest fix: `waha_message_id` was globally unique, but
WAHA ids are unique per *chat*, not per session, so the webhook's
`update_or_create` would have overwritten one number's rows with the other's.
That's now `UNIQUE(session, waha_message_id)`, with `WhatsAppContact` similarly
keyed `(session, phone)` because a LID is issued per linked device — the same
customer has a different LID on each number, and the two contact syncs would
otherwise have flapped that field on every cron pass.

New `whatsapp/sessions.py` is the single resolver (normalize/validate, resolve
from request, resolve from a `WhatsAppSenderRoute` section, list live sessions,
map session → our own number, render the tab strip). Session tabs appear on
wa-dashboard, wa-chats and the CRM inbox only once a second session exists, so
the single-number UI is unchanged. LID matching is scoped per session
everywhere; phone matching deliberately still spans sessions so a lead's history
stays unified. The agent claim queue now defaults to one session with
`?session=all` as the explicit opt-in — widening a claim queue silently would
have let one consumer drain the other number's inbox. The two cron commands loop
over every linked session when `--session` is omitted, so adding a number needs
no crontab edit. Order traffic now sends via the `orders_tasks` route instead of
the global default session.

Also reconciled `deploy/waha/docker-compose.yml` with what was actually running
(it had drifted: claimed NOWEB/single-session, missing `WHATSAPP_DEFAULT_ENGINE`
and `NODE_OPTIONS`), pinned the image off `latest`, and cut the node heap from
16 GiB to 4 GiB under an 8 GiB container cap — the host has 15 GiB and no swap,
so the old setting let one session OOM the whole box.

Verified: 20 new tests in `whatsapp/tests_sessions.py` (55 pass across
whatsapp/core/crm), both constraints confirmed present in the live DB with the
old global unique gone and all 6,183 messages intact, both ops pages rendered
with no unsubstituted placeholders, and `sync_wa_contacts` run for real against
production (8,524 seen, 289 created, 166 updated). Site returns 200 after
reload. Not yet done: creating the `fleet` session and pairing 97466124545 —
that needs a QR scan, and the routing stays on the current number until
`waha_session` is filled in on the instance row.

## 21:15 — wa-dashboard: add-a-number button + section routing panel

Asked whether the multi-number setup could be driven from `/waha/wa-dashboard/`.
It couldn't: the page could start/stop/logout/QR an *existing* session, but had
no way to create one, so linking a second number still needed a curl. Added a
"+ Add number" control to the session tab strip — it prompts for a session name,
validates it against the same `^[a-zA-Z0-9_-]{1,64}$` rule WAHA itself enforces,
POSTs to `/waha/api/sessions`, then lands on the new session's tab so the QR
pane is one click away. The tab strip now always renders on the dashboard (not
only at two-plus sessions), otherwise the control to create the second session
would itself be hidden until a second session existed.

Also added a read-only "Sections sending from this number" panel showing all
four `WhatsAppSenderRoute` sections and the number each resolves to, with rows
for the session on screen highlighted. It deliberately distinguishes *routed*
from *mapped*: a route can point at an instance whose `waha_session` is blank,
in which case Evolution routes to that number but the WAHA send still leaves
from the default session. Showing the instance's phone without that caveat would
have claimed a number was live on WAHA when it isn't — right now all four
sections report "no WAHA session → default", which is the accurate current
state. Editing stays on the staff-authed Auto Triggers / WhatsApp Instances
pages (the dashboard is only htpasswd-gated, so it shows but never writes) and
the panel links to both.

Verified: 63 tests pass (8 new covering section-route resolution, the
routed-but-unmapped case, disabled routes, and dashboard rendering); the
dashboard renders with no unsubstituted placeholders; and `POST /api/sessions`
was probed with a deliberately invalid name — returns WAHA's own 400 validation
error and creates nothing, confirming the endpoint the button calls is live.

**Files:** `whatsapp/sessions.py`, `whatsapp/wa_dashboard_view.py`, `whatsapp/tests_sessions.py`

## 22:50 — WhatsApp Instances: WAHA Session picker instead of a free-text box

The "Edit settings" link lands on WhatsApp Instances, where **WAHA Session** was
a bare text input with placeholder "e.g. default". A typo there fails silently —
sends go to a session WAHA doesn't have, with nothing on screen to explain why.
Replaced it with a `<select>` of the live WAHA sessions (name — phone — push
name, plus the status when not WORKING), shared by the add and edit modals via
`workforce/parts/_waha_session_options.html`, with a link across to the WAHA
dashboard for linking a new number first.

The WAHA Session table column now reports four distinct states rather than
"value or blank": **Linked** (green, with the number), **No such session** (red,
"sends will fail"), **Not set** (falls back to the default session, named), and
**Unverified** when WAHA is unreachable — that last one matters so a WAHA outage
doesn't make every correctly-configured row look broken. Saved names WAHA no
longer reports stay selectable under a "Saved but not found" optgroup, and the
edit JS re-adds a stray value as an option, because assigning an unmatched value
to a `<select>` selects nothing and would have silently blanked the field on
save.

Fixed a bug introduced in the same pass: two `{# ... #}` comments spanned
multiple lines, which Django does not support, so the comment text rendered into
the page. Caught by loading the page as a real superuser rather than trusting
the template to compile; now asserted by a test that no `{#`/`{%` survives
rendering.

Verified: 36 whatsapp tests pass (6 new — picker markup, the three row states,
WAHA-unreachable, orphan retention, and a real POST proving the picker's value
persists to `waha_session`). Confirmed live that the dashboard's "+ Add number"
button works end to end: session `FleetAdmin4545` now exists in SCAN_QR_CODE,
awaiting its QR scan. Container is at 3.07 GiB with two sessions, host has
8.6 GiB free. Note the running container is still the pre-existing one — the
compose `mem_limit` and the 4 GiB heap cap only take effect on recreate.

## 23:10 — WhatsApp Instances: explain what an "instance" actually is

The Add/Edit modal listed Label, Instance Name, WAHA Session, Phone Number with
almost no explanation, and the genuinely confusing part went unsaid: a row is
ONE WhatsApp number, and two of those fields are that same number's name on two
different senders (Evolution vs our own WAHA bridge). Added a short explainer
block at the top of both modals via `parts/_waha_instance_help.html` saying
exactly that, tagged the two backend fields with `Evolution` / `WAHA` badges so
the pairing is visible at a glance, and gave every field a one-line description
of what it's for and what breaks if it's wrong.

Also reordered to identity-first (Label → Phone Number → the two backend
handles), since Label and Phone describe *which number this is* while the other
two are wiring. Field ids were left untouched — `editInstance()` sets them by id
— and a test now asserts all seven still exist so a future relayout can't
silently break the edit modal.

Verified: 38 whatsapp tests pass (2 new), page renders as superuser with no
leaked template syntax, and the modal was read back as plain text to check it
actually scans in order.
