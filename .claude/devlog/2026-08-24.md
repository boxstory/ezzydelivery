## 12:20 — Enforce "Suspended" business status

Setting a seller to Suspended on the staff seller page was previously almost cosmetic — the only
runtime check on `business_status` anywhere in the codebase was the first-mile pickup gate, so a
suspended seller could still add/edit/delete orders, push orders through their API key, receive
Shopify/WooCommerce webhook imports and run temp-order sync. Added `business/suspension.py` as the
single source of truth (`SUSPENDED_STATUSES`, `is_business_suspended`, a content-negotiated
`suspended_deny` that returns HTMX-200/JSON-403/redirect as the caller expects, and the
`business_active_required` decorator), then applied it across ~30 order-write views, the returns
flow, the DRF key authenticator, the inbound webhook receiver, the three pull-import endpoints, the
four temp-order sync sources and the AI-agent import resolver. Suspension is read-only, not a
lockout: the seller still sees their orders, statements and invoices, staff are exempt so held COD
stays reachable, and only `suspended` blocks — `pending` (the default for every new signup) and
`inactive` are untouched.

On the client side, added a persistent `bcon__alertbar` notice to the dashboard base template, made
the integrations/API-keys page render its controls inert with an explanation, and split account
standing from identity verification so the owner still reads "verified" while a separate badge
reads "Business Suspended". Also fixed two staff-side bugs that undermined the feature: approving a
profile no longer silently flips a suspended business back to active, and suspended sellers now
appear on the inactive-sellers page and in the seller stat cards. Credentials are never
deactivated, so lifting a suspension needs no key regeneration. 24 new tests pass; the 6 failures
in `orders`/`business` reproduce with the gate disabled and are pre-existing at HEAD.

## 18:35 — One device per driver, with a WhatsApp confirmation gate
Drivers are now limited to one live device. Signing in on a new phone retires the old one, and a phone we have never seen has to be confirmed with a 6-digit WhatsApp code before it can be used. There is no hardware id to hang this on — no browser exposes IMEI, and neither do modern native apps — so the device identity is a random server-issued token in an HttpOnly cookie, which is stronger than IMEI anyway since nobody can read it off the handset. The retired device is flagged inside its own session rather than deleted, so it can tell the driver why it stopped working instead of dumping them on a blank login page. Ops get a console at /workforce/driver-devices/ to release a device when WhatsApp is down (the chosen fallback) or revoke one, and the switch history there is the account-sharing signal. Two bugs the tests caught: the revoked-session check was swallowing the login POST of a driver signing back in, and the revocation flag survived Django's session-key cycling and would have signed them straight back out. Whole rule sits behind DRIVER_DEVICE_ENFORCEMENT so ops can drop it without a deploy; off during tests so driver fixtures don't land on the gate.
