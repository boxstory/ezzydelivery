# Dev Log — 2026-09-13

## 00:57 — Mandatory proof of delivery, per client
Some clients contract for evidence that a parcel reached the customer (or really could not
be handed over), so proof of delivery is now a rule staff can switch on per client instead
of an optional photo the driver could skip. Three new fields on `Business`
(`pod_required_delivered`, `pod_required_failed`, `pod_kind` = photo / signature / both) are
edited on a new staff console at `/workforce/delivery-app-control/`, listed under Tasks in the
sidebar. The rule itself lives in one place, `delivery/pod.py`, and is enforced server-side on
the driver completion API and on the partial-delivery endpoint — the driver app only mirrors it,
so a direct post cannot slip past. The driver sheets grew what they need to satisfy it: the
Delivered photo label now flips to "required", a signature pad appears when the client asked for
a signature, the Failed sheet gained an attempt photo (it had none at all), and Partial uploads
its proof before submitting because that endpoint speaks JSON. A failed attempt always resolves
to a photo — there is no customer present to sign for a parcel they did not take.

## 01:14 — Live tracking is now a per-client setting, and the map is thinner
Fixed the flaky pickup date-range test first: it formatted its day string from `timezone.now()`
(UTC) while the view reads the From/To boxes as Qatar dates, so the window shifted three hours
and the test failed on any run after 21:00 UTC. It now uses `timezone.localtime()`.

Client live tracking existed but was ungated — every client had the sidebar link and the map
carried a staff-sized popup. It is now a switch on the Delivery App Control page next to the
proof rules (`Business.live_tracking_enabled`), and the client sidebar link only appears when
it is on, with a badge counting deliveries on the road so it lights up the moment a driver taps
Start Ride. Existing active clients were backfilled to enabled so nobody lost a working feature.
The map payload was cut back to what a client following a driver actually needs — task number,
status, the two points, and how old the driver's fix is — with no customer name, phone, address
or driver identity going over the wire. A driver whose app has gone quiet for ten minutes now
greys out and says so instead of looking like a parked bike. Also fixed the tenant filter to
match on the order's business as well, since `DeliveryTask.business` is null on older rows.

## 02:31 — Delivery App Control: one Save in the table header, only for edited rows
Replaced the 25 per-row Save buttons with a single Save in a bar above the table. The bar stays
hidden until a row is actually edited, then reports how many clients are changed and offers Save
changes / Discard; edited rows carry a yellow marker while the change is still only in the browser.
A beforeunload guard stops paging or searching away from pending edits.

The per-row design existed to dodge a real footgun — a blanket submit would rewrite every client on
the page from whatever the checkboxes happened to render as. The new save keeps that protection by
sending only the rows the page's dirty tracking found, so a client nobody touched is never written.
The new endpoint validates the whole batch before writing anything and applies it in one
transaction, so a bad proof type or a stale client id rejects the batch rather than half-applying
it. Both saves now share one `_apply_dac_rules` helper, so they cannot drift on what is logged or
which cache is dropped.

Fixed two Django comment bugs found by screenshotting rather than assuming: multi-line `{# … #}`
is not a comment, and one was rendering its text onto the console page while another sat inside the
driver task card's attribute list. Both are now `{% comment %}`.

## 02:40 — Dashboard "Online" drivers counted approvals, not who is working
The Active Drivers tile on the staff dashboard read 5 while one driver was actually online. It was
counting `driver_status='approved'` — the size of the approved fleet — under a chip that says
"Online". Those are different questions: approval is about the account being in good standing,
availability is about whether anyone is working right now. The database agreed with the report:
5 approved, of which 1 available and 4 offline.

The tile now counts availability, via a new `ONLINE_AVAILABILITIES` constant in fleet/models.py so
nothing else re-invents the definition. Anything but 'offline' counts as on shift — a driver on a
break or driving back from a drop is still working. The fleet size was not dropped, it moved
alongside as "1 of 5", so the tile still answers "out of how many". Checked the other tiles on the
page: COD/Orders/Sellers all describe what they actually count.

Caveat worth knowing: availability is self-reported by the driver app, and the hourly
expire_stale_availability job only forces someone offline after 12h of no activity, so a driver who
closes the app without going offline can read as online until then.

## 02:54 — CRM Driver: a map of where applicants signed up
New page under CRM Driver at /workforce/crm/driver/map/. One pin per driver lead, placed at the
location the applicant's browser captured when they submitted at /join_us/driver/ — that already
sat unused on the Driver row as driver_meta['registration_location'], and Driver Verification was
the only page plotting it. Leads bind to their application by the driver FK, never by phone, so a
card with no application behind it simply has no pin and the note under the map says how many.

Pins are coloured by the stage's outcome — in the pipeline, approved, rejected — rather than by
stage, because a board with nine columns would need nine colours nobody can tell apart; the stage
name, phone, account status, owner and capture accuracy are all in the popup, which links straight
to the lead. Stage, source, owner and search narrow the set, and the map is built from the whole
filtered set rather than a page of it. The view frames Qatar on open with a Fit every pin button,
since people do apply from abroad. Live numbers: 344 of 628 driver leads carry a location.

Three bugs caught while building, all by measuring rather than assuming: the filter selects
collapsed to 1px because main_dashboard_scripts hands every filter select to Select2 and the page
was not using the CRM toolbar classes that account for it; the Apply button sat 1px short of the
pickers beside it; and the accuracy symbol rendered as a literal ± from a double-escaped JS
string. Fixed a fourth found by the tests: the stage filter was validated against the board's
configured columns and silently returned every lead when a stage did not match, and popup names
carried the ZyDrv phonebook tag meant only for the Google Contacts export.
