## 19:38 — REST order API for sellers on a custom website (gooey)
Sellers not on Shopify or WooCommerce had no way in: the generic inbound webhook maps snake_case keys only, so a storefront posting `orderNumber`/`customer{}`/`items[]` lost the customer name entirely and — worse — mapped `total` straight onto `cod_amount`, billing a card-paid order as cash on delivery. Added a small dedicated API in `ezzy_api/store_api.py`: `POST /api/v1/store/orders/` creates one order from the storefront's own camelCase shape, `GET /api/v1/store/orders/<ref>/` returns its delivery status and public tracking link, and `GET /api/v1/store/ping/` lets an integrator verify the key before going live. Auth is the existing ClientApiKey (Bearer or X-API-Key); the tenant is always the key's own business, never a body field, and a suspended or still-pending account is refused. Payment method decides COD — only `cod`/`cash`/`cash_on_delivery` put money on the driver, everything else lands as `online_paid` with zero to collect. Repeat posts of the same `orderNumber` return the existing order with `duplicate: true` instead of creating a second delivery, so a timed-out retry is safe. Orders arrive as `to_review` with `platform='api'` like every other import.

On the staff side, Test Connection now does something useful for a `custom` integration instead of saying "not implemented": it reports whether a live API key exists, its scope and last use, and lists the orders that have actually arrived. Registered gooey's integration row (business 731081) and its API key so the connection shows on the seller's Integrations tab, and wrote the client-facing spec at `/api/docs/custom-website/` with the field table, the COD rule, retry behaviour and curl/Node/PHP examples. Two orders posted while testing against production were removed afterwards.

**Files:** `ezzy_api/store_api.py`, `ezzy_api/tests_store_api.py`, `ezzy_api/urls.py`, `ezzy_api/views.py`, `ezzy_api/templates/ezzy_api/docs/custom-website.html`, `ezzy_api/templates/ezzy_api/docs/*.html`, `workforce/views.py`, `workforce/templates/workforce/seller_api_test_result.html`

## 20:29 — Store order lookup returns the whole order, not just its status
`GET /api/v1/store/orders/<ref>/` answered with the status cluster only — order number, statuses, COD, tracking link — so a seller asking "what do you have for GOOEY-429869?" could not read back the customer, the lines or the amounts. The lookup now returns the full record: `customer` (name, phone, composed address, zone/street/building, coordinates and whether the address has been verified), `items` (name, sku, qty, unit and line price), `amounts` (items total, delivery fee, COD), `package`, and `received` — the untouched JSON we were sent, which is what settles an "I sent you X" dispute. The create response stays the compact summary. Items and the delivery task are prefetched so the extra detail is not N+1.

Fixed a money-formatting bug found by the new test: `str(order.cod_amount or 0)` returned `"0"` for a zero amount because `Decimal('0.00')` is falsy, while any other amount came back as `"65.00"` — the same field in two shapes for the client to parse. All amounts now go through a `_money()` helper and are always two decimals.

**Files:** `ezzy_api/store_api.py`, `ezzy_api/tests_store_api.py`, `ezzy_api/templates/ezzy_api/docs/custom-website.html`

## 21:05 — Custom API tab in the Mapping Manager, fed by a pasted sample payload
Custom API connections had no mapping at all: the store endpoint carried hardcoded guesses at the key names (`orderNumber`, `customer.name`, `items[]`), so the next seller whose storefront calls them `ref`, `buyer.mobile` and `basket[]` would have needed a code change. Added a **Custom API** tab to the Mapping Manager alongside Shopify/Woo/Sheet/OneDrive, storing `{our_field: json.path}` in exactly the same shape as every other platform. Because an inbound integration has no header row and nothing to fetch from, the pickable "columns" come from a **Paste Sample JSON** box: staff paste one real order, we walk it and return every field path, cache them on the integration's `last_headers`, and the existing dropdowns do the rest. Nested keys read as `customer.name`; a list yields both `items[0].name` and a collapsed `items[].name` that stands for every element — so mapping `product_1 → basket[].title` and `count_1 → basket[].count` carries a whole variable-length basket through the two fields every other import source already uses.

Path resolution and discovery live in the new `ezzy_api/json_paths.py` (pure functions, no models) so the endpoint that consumes a mapping and the staff screen that builds one cannot drift. `store_api` applies a saved mapping wherever staff set one and falls back to the built-in guesses for anything left unmapped, so gooey — configured today with 13 mapped fields — keeps working either way. The mapping is written to `BusinessApiSettings.column_mapping`, which is what the endpoint reads; saving only to `Business.import_mapping` would never have reached an inbound order. Also added `custom_api` to the six duplicated "is this mapping nested?" platform tuples, otherwise a business whose only mapping is this one would have been misread as legacy-flat and shown on the CSV tab.
