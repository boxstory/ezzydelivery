## 12:31 — GPS flag threshold raised to 3 km, queue re-backfilled
Raised `DELIVERY_GPS_FLAG_KM` from 1.0 to 3.0 — at 1 km the review queue held 563 flags nobody could
work through, and a 1-2 km gap in Doha is usually a tower fix or a compound entrance rather than a wrong
pin. The value lives in the project-root `.env` (the settings.py default was only a fallback), so both
were updated. Re-running the backfill alone would have been a no-op, because it only ever creates
reviews — so it gained a `--prune` flag that closes still-pending flags the current threshold would no
longer raise, while never touching a review that already carries a verdict. Ran it: 1 new review opened,
76 sub-3 km pending flags closed, 488 left in the queue (min gap 3.03 km, average 12.7). A second run
closes and opens nothing, so it is safe to re-run after any future threshold change.

**Files:** `.env`, `ezzydelivery/settings.py`, `delivery/management/commands/backfill_location_reviews.py`

## 12:38 — Fixed: every verdict on Location Review failed with "Network error"
The decision buttons could never work. The page had no `{% csrf_token %}`, so the JS fell through to
reading the token from `document.cookie` — which `CSRF_COOKIE_HTTPONLY = True` makes impossible — and
posted an empty token. Django answered 403 with an HTML error page, `resp.json()` threw on the HTML, and
the catch block reported it as "Network error", hiding the real cause. Added the token to the decision
bar and dropped the dead cookie fallback. Also rewrote the error handling to check `resp.ok` first and
name the actual failure (403 = stale session, other codes by number) instead of blaming the network.
No data was ever at risk: CSRF rejects the request before the view runs, so no coordinates were moved by
the failed attempts. Verified the whole path — token in the DOM, POST returns 200 JSON, verdict recorded
and coordinates moved — inside a rolled-back transaction so production data was left untouched.

**Files:** `workforce/templates/workforce/delivery_location_reviews.html`

## 13:12 — 17 new zone areas imported from OpenStreetMap (not Google)
Added area names to the zone areas table from OSM rather than Google Places: Google has no Maps key here
and its terms forbid storing Places content in your own database (only place_id may be kept), while OSM is
ODbL and the Qatar extract is already on this server for OSRM. Overpass returned 130 place nodes for Qatar;
after deduplication 17 were genuinely new and are now in — Souq Waqif, Mina District, West Bay, Katara, the
six Pearl/Lusail quarters, Barwa City, Al Ain Gardens, Qatalum Village and four rural areas. Table went
743 -> 760. Deduplication needed three layers, because English transliteration is exactly what varies:
canonical Arabic comparison (which alone caught Fereej Ibn Dirham = Al Mansoura, where the English names
share nothing), transliteration-folded English, and distance only as a referee — folded English on its own
paired Al Numan with Umm Ain 98 km apart. A final per-name check before insert caught two more duplicates
the rule had missed: Al-Shahaniya (already there as Al Shahniya) and a compound "Al Hitmi / Al Rufaa" whose
two halves both already existed. Three of the new rows have no Arabic name in OSM; every one has coordinates.
