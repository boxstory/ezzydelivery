## 14:35 — Daily WhatsApp inbox triage onto the CRM boards
The WhatsApp inbox had never been worked: 893 untriaged senders, 1,242 distinct
inbound numbers, and zero leads ever promoted from it. Added a nightly command
that reads each recent conversation with an AI model, decides whether the sender
is a driver applicant or a business prospect, and files only the confident ones
onto the matching board — anything unclear (greetings, suppliers, personal
messages, spam) stays in the inbox for a human. Runs daily at 05:00 UTC / 08:00
Qatar, after the WAHA backfill, capped at 60 conversations and the last 7 days so
the historic backlog is not dumped onto the boards in one go.

Duplicate protection was the main requirement: a number is skipped if it already
has a lead in ANY stage (`create_lead_from_wa_number` only dedupes against open
ones, so a rejected applicant writing back would have got a second card) or if a
driver application exists, since the driver board builds and maintains that card
itself in `reconcile_driver_leads`. Driver leads start in the `no_driver` column
("New Application") rather than the board's `Incomplete` fallback, which would
have claimed they had a half-finished form. Each card is pinned to the exact chat
(`wa_session` + `wa_chat_override`) and carries the transcript in its notes.

Triage picks its own model (`CRM_TRIAGE_AI_PROVIDER`, default groq
`openai/gpt-oss-120b`) because the shared `AI_CHAT_PROVIDER=router` stack is
currently returning 400 "OpenCode free tier" and its zhipu fallback is 429ing;
it falls back to the chat stack if the triage provider is unset. Verdicts are
cached against the conversation's last message, so an unchanged chat is never
paid for twice and a new message re-reads it at once. Also extracted the inbox's
169-line sender-collection block out of the view into `crm/wa_inbox.py` so the
cron and the page cannot drift apart. First real run filed 4 driver leads
(#797-800); 13 new tests, full crm suite 114/115 (the `ConvertTests` failure is
pre-existing at HEAD).

**Files:** `crm/wa_inbox.py`, `crm/wa_triage.py`, `crm/management/commands/triage_wa_inbox.py`, `crm/tests.py`, `workforce/crm_views.py`, `ezzydelivery/settings.py`, crontab

## 13:52 — Driver payout worksheet: From / To / KM columns
Split the single "Route" column on the verification queue into separate **From** and **To** columns and added a **KM** distance column beside them. ## 15:16 — Payout worksheet: Save fees button
Added a Save action to the queue toolbar that writes edited driver fees without changing any verification status — the step between "that figure is wrong" and "I'm ready to verify it", which the desk previously had no way to express since the only way to persist a fee was to verify or publish in the same click. ## 17:22 — Pickup column reduced to self / hub / transfer, with the handing driver named
The column was showing raw driver codes, which told staff nothing about how the parcel
reached the driver. It now answers in one word: "self" when this driver collected from
the client, "hub" when they took it off a shelf (a hub-delivery leg, or another driver's
drop), "transfer" when another driver handed it over — and on a transfer the handing
driver's name sits on a second line, since the first mile belongs on their sheet. The
state is read off the pickup's status, not its disposition: 2 of 22 hand-offs were filed
as 'self_deliver' and then claimed by someone else, and the status is what happened.
Self outranks hub so a driver who collected and then dropped at a hub still gets the
credit. Sorting ranks self > hub > transfer > none; the CSV keeps the driver code and
disposition alongside the word for reconciliation.
