## 08:59 — Fix silent COD zeroing on Order Edit / Task Edit (root cause of #2044)
Root cause of the BMS045-2044-AB162 COD wipe: OneDrive-imported orders store cod_status_by_client=None; the Order Edit COD Status dropdown had no blank option, so the browser displayed the first choice ("Online Paid") as selected, and any save then hit the view rule "online_paid → force cod_amount=0" — silently wiping COD on orders staff edited for unrelated reasons (e.g. address fixes). Fixes: (1) order_edit.html now renders a "— Not set —" placeholder selected when the status is empty (empty post = no change); (2) order_edit view forces COD to zero only when the status actively CHANGES to online_paid; (3) both order_edit and delivery_task_edit now leave cod_amount untouched when the field posts blank — staff must type 0 to clear. Verified: edit page for an unset order (#2043) shows the placeholder selected and online_paid unselected.

**Files:** `workforce/templates/workforce/order_edit.html`, `workforce/views.py`

## 09:18 — Friendly CSRF failure page (login "Page Expired" UX)
Investigated ezzyadmin's CSRF error on sign-in: gunicorn journal showed "CSRF token from POST incorrect" on /accounts/login/ — a stale login tab submitting after the token rotated (user was already logged in in another tab). Config was fine, so instead of Django's raw 403 we now have a custom CSRF_FAILURE_VIEW: /accounts/ pages redirect back with an "expired — try again" message (or straight to the dashboard if already authenticated), AJAX gets a JSON 403, and other pages render a branded "Page Expired" card with a same-origin Go Back link.

**Files:** `core/views_csrf.py`, `core/templates/core/csrf_failure.html`, `ezzydelivery/settings.py`
