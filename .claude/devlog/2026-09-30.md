# Dev Log — 2026-09-30

## 00:15 — Driver leads board: five application facets + search reaches the application

The driver kanban could only be narrowed by source, assignee, vehicle and created
date, so a recruiter could not ask the questions the job is actually about. Added
five facets covering the rest of the driver application behind each card: job type,
uploaded documents, working hours, language and preferred zone. Keys, options and
meanings are deliberately the same as the driver verification queue's bar, so a URL
reads the same on both pages and "Part Time" means one pool across the desk. The
documents facet is a completeness reading, not a row count — Complete is the public
application's own rule (a selfie plus two distinct ID types, each holding a real
uploaded file rather than the placeholder the model ships with), Partial is something
uploaded but short of that, Missing is nothing at all. On the live board the three
buckets partition it exactly: 522 + 91 + 310 = 923.

The search box also now reaches into the application: a number matches the driver's
own phone and WhatsApp number, and a name matches their driver code and account name.
A driver who applied from one number and chats from another was unfindable by the
number staff had in hand — the two disagree on 46 of the 821 linked driver cards.

Bar layout: nine controls in the single row the business board uses would measure
past 1500px and shove the scope readout off the card, so the driver bar gets a
`crmb__filters--rich` modifier that flows the facets five-up over two rows (four
between 768 and 1199px). The fixed 8.25rem track is kept — Select2's percentage width
contributes nothing to intrinsic sizing, so an auto-fit track collapses to one column.
The rule is held above 768px so the existing phone layout is untouched.

Every facet fails open: an unknown value from a stale or hand-edited URL narrows
nothing rather than emptying the board. Zone is a reverse many-to-many and gets a
distinct, so an applicant who picked three zones is still drawn once. Ten new tests
in `crm.tests.DriverBoardApplicationFacetTests` cover each facet, the AND/OR
semantics, chip removal, the fail-open contract and the search change.

Pre-existing, not touched: `crm.services.reconcile_driver_leads()` runs on every
driver board load and is 671 queries on its own (563 of them ZoneGroup), which is
~96% of the page's query count.

## 15:31 — Driver filter lists the working fleet again, not just app sign-ins
Yesterday's change narrowed the shared staff driver picker to drivers holding an active
`DriverDevice`, which turned out to be the wrong question: a device row is revoked the instant a
driver signs in on a new handset and the replacement sits at `pending` until the WhatsApp code
lands, so Rahees — 420 tasks in 60 days, the busiest name on the board — disappeared from every
list, along with Nazeem and Ismail, who have tasks but were never issued a device. The pool is now
approved drivers plus anyone who already carries a delivery task (15 options instead of 4, built
with EXISTS so many device rows can't duplicate a name), and app access is *reported* on the
option as "· app" instead of deciding who appears. Verified on all eight lists that use the
helper: 16 options each, 4 app-marked, picked drivers still selected. 7 new tests.
