# Dev Log — 2026-08-21

## 12:30 — Fix ERR_TOO_MANY_REDIRECTS on business dashboard login
A client (`ladeen_admin`) could not reach `/business/dashboard/` — the browser died with ERR_TOO_MANY_REDIRECTS. Cause: `main_dashboard` redirected to the business dashboard purely on the `profile.is_business` flag, but the dashboard's `@business_required` gate needs a real Business row (or an active + staff-verified team membership); when the flag and the data disagree the two views bounce off each other forever. `main_dashboard` now resolves actual business access before redirecting, and `business_required` sends business-flagged users with no business record to `/business/register/` (a terminal page) instead of back to `main_dashboard`.

Verified with the Django test client: owners and verified team members still land on the dashboard in 200/0-hop, and the two affected accounts (`ladeen_admin`, `testbusiness`) now terminate at business registration instead of looping.

Data fix for the affected client: `ladeen_admin` (user 134) had `is_business=True` + verified but no Business row, while the LaDeeN business (900262, same email) was owned by user 889. Linked user 134 to LaDeeN as an active, staff-verified `manager` team member (BusinessTeamProfile id 99) rather than transferring ownership. Confirmed with a real production login: `/accounts/login/` → `/dashboard/` → `/business/dashboard/` returns 200 with LaDeeN data. `testbusiness` (id 80, stale test account) was left as-is at the registration page.

**Files:** `core/views.py`, `core/decorators.py`

## 15:35 — 3PL pricing WhatsApp: destinations moved out of the source onto the Auto Triggers page
Answering "which number does the 3PL pricing form send from" turned up four phone numbers written into Python. The sender was already configurable (the CRM — Business Leads route), but the *destinations* were not: both quote alerts posted to a literal `97466451589`, the CRM follow-up digest used a module constant for unassigned leads, and the public "Chat on WhatsApp" button on the pricing page opened a chat with a literal number that nobody could change. Added a per-trigger `notify_number` on AutoTriggerConfig with a "Sends to" line in the row and a picker (our numbers, or Other number…) in the trigger Edit modal, backed by a code-defined `RECIPIENT_TRIGGERS` map so only the three triggers that really alert a staff desk get the control. The public chat button now opens the CRM — Business Leads route number, so a prospect lands in the same thread the quote thank-you comes from. The fleet-number fallback for driver-onboarding sends was replaced by a seeded `driver_onboarding` sender route (migration 0029) — same number, now editable on the page.

Resolution is unchanged for every existing send: blank "Sends to" falls back to the platform default instance (97466451589), which is exactly where those alerts went before. Behaviour change to flag: the public quick-inquiry chat button now opens 97460003432 instead of 97466451589. Verified end to end through the real view with the test client — page renders the new column, an 8-digit local number is normalised and stored, a bad number is rejected 400 with the old value intact, a non-recipient trigger ignores the field, and clearing it falls back to the default. `crm.tests.DigestTests` updated (it relied on the removed constant) plus a new test for "no number configured anywhere → skip, never guess".

## 15:51 — Messages tab split out into its own "Message Templates" page
The editable WhatsApp bodies were the fifth tab on the AI Config page, so message copy sat behind provider/model/budget plumbing and only surfaced through a `#msg-…` deep link. They now live at `/workforce/auto-triggers/messages/` as their own console, reachable from a new **Messages** sublink under Auto Triggers in both the desktop and mobile sidebars. Card ids are unchanged (`msg-<key>`), so the "edit the body" buttons on the Auto Triggers composer rows still land on the right card — the view now builds those links from the new URL.

The page is grouped by sender route (Orders & Delivery Tasks / CRM — Business Leads / CRM — Driver Leads), each group showing the number it actually sends from, with a jump bar across the top. Each card gained three things the tab never had: click-to-insert placeholder chips, an "Opens on" list of the staff screens that open with that body, and a Preview that renders the text as a WhatsApp bubble with sample values so bold/italic/line breaks can be checked before saving. Save, the on/off switch, the trigger-owned no-switch case and "Restore default text" behave exactly as before. The write path moved with it — `wf_ai_config` no longer handles `section=templates` and no longer loads message templates, so a message edit never touches `.env` or reloads gunicorn.

Verified by rendering all three affected pages through the real views: the new page returns 200 with a card per registered template, AI Config no longer contains the Messages tab or its JS, and the Auto Triggers deep links point at the new URL.

## 15:53 — Auto Triggers: edit the message body in a popup instead of navigating away

On /workforce/auto-triggers/ the Manual Composer rows had a pen button that was actually a hyperlink to the Messages console, so clicking "edit" on those rows threw you off the page mid-review — and for any desk that is not super admin it landed on a page they cannot even open (the Messages console is admin-only). Those rows now open an in-page popup that edits the body directly: description, on/off switch, textarea, click-to-insert placeholder chips and "Restore default text". Where the on/off belongs to a trigger (`order_verify_manual` → `wa_location_verification`) the switch is replaced by a note pointing at the row that owns it, same rule the Messages page follows.

The two WhatsApp triggers that send a stored body (`wa_driver_application_thanks`, `wa_location_verification`) gained the same popup on a second button, so their wording is editable from the trigger row too. Every row that has a body also shows the extra action button that opens the full Messages console — but only for super admins, who are the only ones it works for. New mapping `core.message_templates.TRIGGER_TEMPLATES` says which trigger sends which body; new endpoint `auto_trigger_message_save` does the write, scoped to the bodies the viewer's own rows send (a finance-only desk gets an empty set and a 403). The Edit column went 7% → 10% with the button padding declared directly, since brandkit-overrides out-declares Bootstrap's padding vars and three default-width buttons overflowed the column by 38px at 1366.

Verified in a real browser: the composer pen opens the popup without navigating, Save posts 200, the modal closes and the status cell repaints; the save endpoint refuses an empty body, an unknown key, and another department's body.
