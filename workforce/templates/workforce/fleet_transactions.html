{% endif %} {% comment %} Filter bar. Filters are added on demand from a searchable "+ Filter" menu and each active one renders as a segmented chip: field | operator | value | x. Nothing is removed — every filter still exists in the form at all times; an inactive chip is hidden rather than dropped, so the GET form always posts the full parameter set and a filter is one click away instead of one of nine boxes competing for attention. A chip is visible when the server says its filter is applied (the `--on` class below) or when the user adds it from the menu. Removing a chip clears its inputs and returns it to the menu. All server-rendered, no framework. The operator segment states the semantics the query actually uses — "contains" for the text search, "between" for the amount range — which were previously invisible. It is a label, not a control: the view implements one comparison per field, so a dropdown offering others would be a promise the backend does not keep. Making them selectable is a backend change. {% endcomment %}
